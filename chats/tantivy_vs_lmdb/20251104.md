# Final Summary

## Validated Results

**Tantivy single-threaded (10K docs/index):**
- Overhead: 8.5 MB
- Commit latency P99: 677ms
- Query: 0.08ms

**Tantivy concurrent (10 indices):**
- Commit latency P99: 3,851ms (5.6x degradation)
- Overhead: 23.4 MB/tenant
- **Failure mode confirmed:** parallel fsyncs serialize, latency collapses

**LMDB (raw storage):**
- Overhead: ~1 MB/10K docs
- Query: 0.012ms
- **Caveat:** measurement likely invalid (mmap not forced resident)

## Critical Finding

Tantivy architecturally incompatible with multi-tenant real-time writes. Cannot atomically commit across indices. At 100 tenants × 1 commit/sec = 100 serialized fsyncs/sec → queue buildup.

LMDB enables cross-tenant batching (single txn spans multiple DBs → single fsync for all tenants).

## Decision

**LMDB required.** Not for overhead savings (projected 8-17 MB/tenant vs Tantivy's 23 MB under load), but because cross-tenant atomic commits are only path to <1s visibility at target density.

## Unknowns Blocking Implementation

**High priority:**

1. **FST overhead on LMDB not measured.** Estimate 5-10 MB/tenant is pure speculation. Could be 20+ MB. This determines if custom build has acceptable overhead.

2. **Sort performance never tested.** Your core differentiator ("sort any field") untested on either stack. If 100K-doc sorts >200ms P99, entire architecture fails regardless of storage choice.

3. **LMDB write throughput under 1000 items/commit unknown.** Test showed 200-300ms single-doc commits, but batch encoding 1000 items might spike to >1s, breaking <1s SLA.

**Medium priority:**

4. **Concurrent read contention on LMDB.** Measured sequential queries, not 20-100 simultaneous readers across tenant DBs.

5. **Segment/compaction strategy undefined.** LMDB grows monotonically without compaction plan. Need vacuum strategy or file size explodes.
